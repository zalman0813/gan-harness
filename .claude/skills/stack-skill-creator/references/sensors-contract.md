# sensors.ini — stack sensor command contract

Every stack skill under `.claude/skills/<stack>/` MUST provide a
`sensors.ini` at its top level (sibling of `SKILL.md`, alongside
`references/`). It declares the lint/typecheck/test commands the
harness gates invoke for this stack.

The harness components that consume `sensors.ini`:

- The project's git pre-commit hook at `.git/hooks/pre-commit` —
  installed by setup-gan-harness-skills. Stripe-style two stages
  (<1s autofix → <5s read-only check). Internal stages cover lint.fix
  → lint.check → typecheck → test.unit → AC literal coverage. AC literal
  coverage is inlined; there is no separate sensor script.
- `.claude/skills/evaluator-handbook/scripts/gate_eval_postcommit.py` —
  evaluator's L1+L2 wrapper (full `module_path` scope + optional L5
  smoke). The evaluator's grading process verifies AC literal coverage
  independently as the GAN-pattern adversarial check (per
  `evaluator.md` Principle #4); this gate handles only L1/L2/L5.

## Required sections and keys

| Section | Required keys | Optional keys |
|---|---|---|
| `[lint]` | `fix`, `check` | — |
| `[typecheck]` | `command` | — |
| `[test]` | `unit` | `smoke` |

`configparser` (Python stdlib) is the parser. Comments use `#` or `;`
at line start.

## Placeholder

The harness substitutes this in any command string before execution:

| Placeholder | Substituted by | Value |
|---|---|---|
| `{scope}` | git pre-commit hook / `gate_eval_postcommit.py` | pre-commit: changed files (`git diff --name-only`); eval: `feature.module_path` (L1), `feature.test_contract.l2_path` (L2), or `feature.test_contract.l5_smoke_path` (L5) |

ALWAYS quote `{scope}` in the command string if your tool is
whitespace-sensitive (most modern lints handle multiple paths).

## Typecheck command MUST be production-faithful

The `[typecheck] command` is run by both the pre-commit hook AND the
evaluator's `gate_eval_postcommit.py`. Its job is to catch **everything
production deploy would catch** — not "minimum tsc". Mismatch here is
how within-batch debt slips past evaluator and surfaces in a downstream
feature's commit.

Concrete trap (Next.js): `tsc --noEmit` alone misses Next.js's strict
route validation, because that validation is encoded in
`.next/types/**/*.ts` which is auto-generated by `next build` / `next dev`.
On a fresh checkout `.next/types/` doesn't exist, so tsc silently skips
the strict route checks. An earlier feature can then ship a route file
with an invalid named export, evaluator says PASS (because tsc was
incomplete), and a later feature in the same batch hits the failure
when something in between regenerates `.next/types/`. **Use `next build`
as the typecheck command** — it regenerates `.next/types/` then runs
tsc; production-faithful by construction.

Generalised rule: pick the typecheck command that the **production
deploy pipeline** would run. If your stack has a "build" step that
performs additional validation beyond your bare type-checker (route
contracts, schema generation, codegen, etc.), prefer the build step.
Cost-vs-correctness tradeoff: production-faithful is slower, but
catching debt at evaluator time costs vastly less than letting it
leak to a downstream feature.

If the production-faithful command is too slow for the pre-commit hook,
add an OPTIONAL `[typecheck] strict_command` key: hook reads `command`
(light), evaluator reads `strict_command` first then falls back to
`command`. Don't preempt this asymmetry — only split when speed becomes
a real, measured problem.

## Empty values = skip

If a key value is empty (e.g., `smoke =`), the harness skips that step
silently. `gate_eval_postcommit.py` will not error on an empty `smoke`
even when `feature.test_contract.l5_smoke_path` is set; it logs a
SKIPPED note.

## Known limitation: dual-consumer scope semantics

The same `[test] unit` line is consumed by **two callers with different
scope semantics**:

| Caller | What `{scope}` is substituted with | What the runner should do |
|---|---|---|
| Pre-commit hook (`.git/hooks/pre-commit`) | Changed files (`git diff --name-only`) — typically a mix of source + test files | Run only the tests covering those changes |
| `gate_eval_postcommit.py` (evaluator) | `feature.test_contract.l2_path` (a directory) | Run all tests under that path |

Most test runners' positional CLI args are filename filters (substring
or glob match against test files). That works for the evaluator case
(directory path matches its tests) but is lossy for the pre-commit case
(source files don't match any test filename → 0 tests run unless the
runner has explicit "tests covering this source file" support).

Stack-specific runners that handle the gen-side correctly:
- `vitest --related <files>` (uses Vite's module graph)
- `jest --findRelatedTests <files>` (uses Jest's coverage map)
- pytest has no equivalent — use pytest-testmon or similar

Stacks where the runner does NOT handle source→test mapping should
adopt one of:
1. **Accept gen-side weakness + strong evaluator gate** (the GAN-pattern
   default). Use `--passWithNoTests` (vitest) or equivalent so 0-match
   doesn't fail. Document in sensors.ini comments. Evaluator's full L2
   sweep is the real safety net.
2. **Wait for two-key contract.** If false-PASS becomes a real problem,
   split into `unit_changed` (hook) + `unit_path` (evaluator) — but that
   requires changing both gate scripts; not done today.

NEVER hard-code a path like `__tests__` in place of `{scope}` — that
ignores the "changed files only" contract entirely and runs the whole
suite every commit (slow + defeats the purpose of scoping).

## Self-validation

After emit, stack-skill-creator runs these checks:

1. File exists at `.claude/skills/<stack>/sensors.ini`
2. All required sections + keys present (`[lint] fix`, `[lint] check`,
   `[typecheck] command`, `[test] unit`)
3. Every command string parses as a non-empty token list

A failed check aborts skill creation — fix sensors.ini before retry.

## Template

See `templates/sensors.ini.template` for an annotated Python (Ruff +
mypy + pytest) example. New stacks copy it, substitute commands, and
validate.

## Why a separate file (vs putting commands in SKILL.md)

`sensors.ini` is **machine-readable**: hooks parse it directly. Putting
commands in SKILL.md prose would force every gate to re-implement
fragile markdown extraction. Separating "human prose" (SKILL.md +
references/) from "harness contract" (sensors.ini) keeps each stable.

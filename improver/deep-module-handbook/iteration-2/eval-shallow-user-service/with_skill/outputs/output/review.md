# Design review — `user_service.py`

## Summary

Module under review: `improver/deep-module-handbook/iteration-2/eval-shallow-user-service/with_skill/outputs/input/user_service.py` — a single `UserService` class, ~120 LOC, ~14 public methods over a `UserRepository` dependency.

**Overall verdict: FAIL.** The module is the textbook shallow / leaky / temporally-coupled case Ousterhout warns against in APOSD ch.4–5. Five of foundation.md §5's six red flags fire (`fake-deep-pass-through`, `temporal-coupling`, `wrapper-around-stdlib`, `exception-leak`, `config-leak`) and four of the §3.5 PASS criteria clearly fail (C1, C3, C4, C6). The module also contains independent security failures (raw SQL interpolation, raw password stored unhashed) that the evaluator-slice §4 axis catches.

A note on the contract baseline: no agreed sprint contract exists for this file in the eval substrate, so the §1.6 cross-checks (`hides_decision_falsifiable_within_one_minute`, `applicability_honest`, `boundary_type_honest`) are evaluated against the *implicit* claim of a class named `UserService` — i.e. a domain service in the business-logic applicability row. `drift_from_contract` is therefore empty (nothing to drift from), but the FAIL is driven by the booleans + `design_review` narrative per §7.

## Narrative

The five-axis walk per evaluator-slice §2 collapses cleanly: **A (Depth) FAIL** because a maintainer could reconstruct the implementation from the public signatures alone — every method name announces its body. **B (Leak) FAIL** on `find_users_by_status_raw` (SQLAlchemy Row in the return type) and on `delete_user` (SQLAlchemy exception in the raises list). **C (Pass-through) FAIL** on eight methods that do not survive the foundation.md §5.5 deletion test and do not qualify as ACL per §4 row 4 — they translate no foreign vocabulary, only rename. **D (Boundary translation) FAIL**: there is no anti-corruption layer between the persistence BC and the domain BC; foreign types flow straight through. **E (Mock budget)** is unobservable from the source alone but the C7 prognosis is poor — any test of this class would have to mock the repo and assert the per-method forwards, which is the mockist-drift smell foundation.md §4 row 2 warns against.

The recommended NEGOTIATE-time response, had this module been proposed in a sprint contract draft, is per evaluator-slice §1.5: push back on the entry-point budget (C4) and the implicit `boundary_type: internal` claim before agreeing. The honest reshape is to delete `UserService` entirely, let callers depend on `UserRepository` directly for read paths, and introduce two small genuinely-deep modules where real decisions hide: a password-credential module (hides hashing scheme + verification + rehash-on-login policy — Parnas-named) and an account-state module (hides the locked/active state machine + the transitions that may trigger side effects like audit-log writes). Each would clear C1 in one sentence, satisfy C3 (≥2 callers regrow the logic if removed), live inside the 1-3 entry-point budget, and translate `sqlalchemy.exc.OperationalError` into a domain `RepositoryUnavailable` at the boundary per Bloch Item 73. The current `UserService` does none of these.

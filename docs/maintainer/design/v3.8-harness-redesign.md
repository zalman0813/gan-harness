# gan-harness v3.8 — design memo

**Status**: design lock, pre-implementation
**Supersedes**: existing 4-stage design (`/prd` `/plan` `/execution-loop` `/finalize`)
**Source**: Anthropic v2 ([Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps), 2026-04-23) — fidelity-first, with two deliberate departures (no escalate, archetype-aware criteria)

**Audience**: gan-harness maintainers. Not copied to target projects.

---

## 1. Why this redesign

Current 4-stage design has three pain points the user surfaced:

1. **Planner over-prescribes.** `/plan` produces granular `feature-list.json` with AC + must_not + eval_anchors. Generator gets boxed in; if implementation reveals spec is wrong, generator can't amend → evaluator FAILs three rounds → status:deferred → human fixes. Human is *not* out of the loop.
2. **`/prd` and `/plan` are two stages doing the same thing.** Both clarify intent + structure deliverables. Verbose.
3. **No general lift from the 7-role evaluator proposal** unless we accept Anthropic v2's per-sprint negotiation. Without negotiation, the generator/evaluator roles can't bridge a high-level spec to testable implementation, and the value of separating planner from generator collapses.

v3.8 follows Anthropic v2 verbatim on the structural choices (high-level spec, per-sprint contract negotiation, GAN loop) and adds two adaptations for gan-harness's "human-out-of-loop overnight" target use:
- Removed escalate machinery (Anthropic doesn't have it; gan-harness doesn't need it either if generator pivots strategically)
- Evaluation criteria parameterised by archetype (Anthropic's 4 frontend criteria don't fit backend/lib/CLI/data epics)

## 2. Top-level pipeline

```
USER intent ──▶  /init  ──▶  /loop  ──▶  /finalize  ──▶  archived epic
                  │            │            │
                  │            │            └─ promote ADRs, merge CONTEXT.md,
                  │            │               regen CODEMAP.md, archive
                  │            │
                  │            └─ walk sprint plan, per-sprint:
                  │                negotiate ↔ implement ↔ evaluate
                  │
                  └─ planner (default grill, --no-grill bypass)
                     produces specs/_epic/spec.md (immutable)
```

Three stages. Three agents (planner / generator / evaluator). One optional helper (fact-finder).

Single human checkpoint per stage at most:
- `/init`: approve spec.md (or `--no-confirm` for autopilot)
- `/loop`: zero (operator monitors cost externally)
- `/finalize`: zero or one (review final archive)

## 3. Three agents + helper

### planner
- **Lifecycle**: runs once at `/init`
- **Responsibility**: clarify intent → produce `spec.md` (high-level, immutable through `/loop`)
- **Tools**: read, grep, find, ls, AskUserQuestion (grill), spawn fact-finder (optional)
- **Auto-loaded skills**: `planner-handbook`, `deep-module-handbook`
- **Constraint**: produces high-level only. NO sprint contract details. NO testable AC. NO pre-cooked ADRs except where the three-test gate fires during planning itself.

### fact-finder (optional helper)
- **Lifecycle**: spawned by planner at `/init` for brownfield epics that touch existing codebase
- **Responsibility**: blindfold codebase research, returns file:line evidence to a caller-specified output path
- **Trigger**: planner decides — typically when spec involves modifying existing code rather than greenfield build
- **Skipped for**: greenfield epics with no codebase context

### generator
- **Lifecycle**: per sprint in `/loop`
- **Responsibility**: negotiate sprint contract with evaluator, implement sprint features, self-evaluate, hand off
- **Tools**: read, grep, find, ls, write, edit, bash; `propose_contract`, `propose_contract_amendment`
- **Auto-loaded skills**: `generator-handbook`, `deep-module-handbook`, active stack skill
- **Constraint**: implements one feature at a time within the sprint; self-evaluates before handoff

### evaluator
- **Lifecycle**: per sprint in `/loop` (negotiation + QA)
- **Responsibility**: review contract drafts, run behavioral QA against contract verification_plan, run matrix sensor, threshold-check, return verdict
- **Tools**: read, grep, find, ls, bash (Playwright/curl/test runners + matrix sensor scripts); `review_contract`
- **Auto-loaded skills**: `evaluator-handbook`, `deep-module-handbook`, active stack skill
- **Constraint**: skeptical-by-tuning; never edits source code; only path back to generator is feedback in `_evals/*-feedback.md`

## 4. File artifacts (final)

```
specs/_epic/
├── spec.md                         [/init create, immutable thereafter]
├── contracts.jsonl                 [/loop append-only]
├── _pending/                       [contract drafts in negotiation, ephemeral]
│   ├── S{NN}-draft-v{N}.yaml
│   └── S{NN}-review-v{N}.yaml
├── _evals/
│   ├── S{NN}-R{N}.json             [evaluator verdict, append per round]
│   └── S{NN}-R{N}-feedback.md      [MAIN deterministic merge for next-round generator]
├── _traces/*.jsonl                 [SubagentStop hook, transcript-as-evidence]
└── progress.tsv                    [SubagentStop hook, per-round metrics]

specs/epics/<slug>/                 ← final archive at /finalize

CONTEXT.md                          [keep-alive, /finalize merges new domain terms]
CODEMAP.md                          [keep-alive, /finalize regens from barrels]
docs/adr/NNNN-*.md                  [proposed at /init or /loop, accepted at /finalize]
```

**Removed from v1 / v3.x**:
- `feature-list.json` — features section is now Markdown inside `spec.md`
- `state.md` — state derived from `contracts.jsonl` + git
- `_escalations/` — no escalate mechanism
- `_quarantine/` — no escalate
- `claude-progress.txt` — `_traces/` + `progress.tsv` cover this

**Why no `feature-list.json`**: v2 article (verbatim) does not name any file. Features are in `spec.md` as Markdown sections. JSON anti-drift is achieved instead via `block_pretool.py` enforcing spec.md immutability and `contracts.jsonl` append-only.

**Why no `state.md`**: v2 article verbatim does not mention any state file beyond what git + handoff artifacts provide. State is *derived* — `epic_status.py` helper reads `contracts.jsonl` and `spec.md` to compute current sprint, completion, etc.

## 5. spec.md schema

Markdown, lint-enforced structure (`spec_lint.py`):

```markdown
# Spec — <epic-slug>

## Vision
<2-4 sentences>

## Tech stack
- Frontend: <stack skill name or "n/a">
- Backend: <stack skill name or "n/a">
- ...

## Archetype
<one of: frontend | backend | library | cli | data-pipeline | hybrid>

## Features
### F01 — <name>
**Sprint**: S01
**User stories**: As a user, I want to:
- <story 1>
- <story 2>
**Data model** (if applicable):
- <entity> { <field>, <field>, ... }

### F02 — ...

## Sprint plan
### S01 — <name>
- Delivers: F01
- Depends on: (none | S<NN>)
- Smoke check: <one user-observable verb that signals "this sprint shipped">

### S02 — ...

## Evaluation criteria
<4 criteria pulled from archetype template; planner may reword but not drop>

1. <criterion 1>: <description>
2. <criterion 2>: <description>
3. <criterion 3>: <description>
4. <criterion 4>: <description>

## Cross-cutting constraints
- Design language: ... (if frontend)
- Performance budget: ... (if applicable)
- Non-goals: ... (explicit out-of-scope)

## Overall success criteria
<3-7 behavioral, end-to-end>

## References
- CONTEXT.md (existing domain language)
- ADRs to respect: ADR-NNNN, ...
- (optional) brownfield research: see specs/_epic/_research/
```

`spec_lint.py` rules:
- L01: every `### F{nn}` has Sprint + User stories + (Data model if archetype demands)
- L02: feature names contain no phase markers (backend / api layer / phase 1 / scaffolding / etc.)
- L03: every `### S{NN}` has Delivers + Depends on + Smoke check
- L04: smoke check uses user-observable verb (`user can` / `user sees` / `system shows`), never `code compiles` / `tests pass`
- L05: sprint deliverables touch ≥2 layers OR sprint marked `pure-frontend` / `pure-backend` / `pure-lib` with explicit reason
- L06: overall success criteria has ≥1 behavioral end-to-end check
- L07: archetype is set; evaluation criteria block has exactly 4 entries

## 6. Archetype templates (Q1 resolution)

Planner picks one at `/init` based on tech stack and user intent. User can override.

### frontend (or hybrid with prominent UI)
1. **Design quality** — coherent visual identity, mood, distinct
2. **Originality** — custom decisions vs library defaults vs AI slop
3. **Craft** — typography, spacing, contrast, technical fundamentals
4. **Functionality** — usability independent of aesthetics

### backend (service / API / no UI)
1. **API design quality** — RESTful or RPC consistency, naming, versioning, documentation
2. **Robustness** — error handling, edge cases, idempotency, retry semantics
3. **Craft** — code structure, type safety, observability, test coverage
4. **Functionality** — endpoints work end-to-end, contracts honored, integrations correct

### library / SDK
1. **Interface design** — minimal surface, deep modules, pit-of-success defaults
2. **Originality** — thoughtful defaults vs scaffolded noise
3. **Craft** — API stability, error types, docstring completeness
4. **Functionality** — examples work, edge cases handled, semantic versioning honored

### cli tool
1. **UX quality** — helpful errors, consistent flag style, --help readability
2. **Robustness** — works in pipelines, signal handling, exit codes
3. **Craft** — code structure, subcommand organization, test coverage
4. **Functionality** — subcommands work, end-to-end flows reliable

### data pipeline / batch job
1. **Correctness** — output invariants hold, schema match, deterministic
2. **Robustness** — idempotency, restart safety, error budget, observable
3. **Craft** — modular stages, structured logging, lineage tracking
4. **Functionality** — produces expected output for known input fixtures

Planner is **encouraged to reword** for the specific epic but **may not drop** — always 4 criteria. New archetypes can be added as templates over time.

## 7. contracts.jsonl entry schema

```jsonl
{
  "contract_id": "C-S01-v1",
  "sprint": "S01",
  "features_covered": ["F01", "F02"],
  "phase": "agreed | completed | amended",
  "negotiated_at": "<iso-8601>",
  "done_looks_like": [
    "User can create project via /dashboard with name + description",
    "Project persists to DB with all metadata fields",
    "Project appears in dashboard list within same session"
  ],
  "verification_plan": [
    {
      "kind": "playwright",
      "id": "vp-01",
      "steps": ["navigate /dashboard", "click 'New Project'", "..."]
    },
    {
      "kind": "api",
      "id": "vp-02",
      "steps": ["POST /api/projects", "assert 201", "..."]
    },
    {
      "kind": "test",
      "id": "vp-03",
      "path": "tests/test_project.py"
    },
    {
      "kind": "matrix",
      "id": "vp-04",
      "checks": ["perf:budget", "secret:scan", "mutation:>=0.75"]
    }
  ],
  "criterion_mapping": {
    "<criterion-1-name>": ["vp-01", "vp-02"],
    "<criterion-2-name>": ["vp-03"],
    "<criterion-3-name>": ["vp-03", "vp-04"],
    "<criterion-4-name>": ["vp-01", "vp-03"]
  },
  "thresholds": {
    "playwright_must_pass": "all",
    "api_must_pass": "all",
    "test_must_pass": ">=90%",
    "matrix_must_pass": "all"
  }
}
```

`criterion_mapping` is the bridge from sprint-local verification to the 4 global archetype criteria. Evaluator rolls up verification_plan results into per-criterion scores; threshold check is per-criterion.

Subsequent entries for the same `contract_id` track lifecycle:
```jsonl
{"contract_id": "C-S01-v1", "phase": "completed", "completed_at": "...", "evidence_ref": "_traces/S01-gen-R2.jsonl:L1247-L1789"}
```

## 8. /loop algorithm

```
while exists pending sprint in spec.md:
    S = active-sprint (lowest-numbered sprint not in contracts.jsonl with phase:completed)

    # Phase 1 — Negotiate (per sprint, MUST happen)
    R = 1
    while not agreed:
        generator (fresh ctx) reads:
            spec.md
            contracts.jsonl (last N entries for context)
        generator → propose_contract(S) tool
            writes _pending/S{NN}-draft-v{R}.yaml
        evaluator (fresh ctx) reads:
            spec.md
            draft
        evaluator → review_contract tool
            writes _pending/S{NN}-review-v{R}.yaml
            verdict: approve | amend_request | reject
        if approve:
            MAIN merges, appends to contracts.jsonl with phase:agreed
            break
        else:
            R += 1
            generator amends, repeat
    # Note: no max R — keep iterating until agreed.
    # Anti-spinning: generator-handbook instructs to pivot strategy if 3 rounds same finding.

    # Phase 2 — Implement
    R = 1
    while not passed:
        generator (fresh ctx) reads:
            spec.md
            contracts.jsonl[contract_id matches latest agreed for S]
            _evals/S{NN}-R{R-1}-feedback.md (if R>1)
            _traces/S{NN}-gen-R{R-1}.jsonl[start:end] (if R>1)
        generator implements:
            inner gate (lint + typecheck + unit tests) must green for commit
            commits via git
            (mid-flight) propose_contract_amendment if implementation reveals contract issue
            (mid-flight) propose_feature_add only as discovery (rare)
        SubagentStop hook fires:
            captures transcript_path → writes _traces/S{NN}-gen-R{R}.jsonl
            appends progress.tsv row

        # Phase 3 — Evaluate
        evaluator (fresh ctx) reads (locked order):
            1. spec.md
            2. contracts.jsonl[contract_id matches latest agreed for S]
            3. _traces/S{NN}-gen-R{R}.jsonl[start:end]   ← runtime evidence
            4. git diff HEAD~1..HEAD
        evaluator runs:
            for each verification_plan[] entry:
                run via Playwright / curl / test runner
            run matrix sensor (perf | race | locale | sca | secret | mutation)
        evaluator rolls up by criterion_mapping:
            per-criterion score
        evaluator emits:
            _evals/S{NN}-R{R}.json (per-criterion scores + findings)
            _evals/S{NN}-R{R}-feedback.md (MAIN merged for next-round generator)

        if all-criteria pass thresholds:
            contracts.jsonl append phase:completed
            break inner loop
        else:
            R += 1
            generator must strategic-decide: refine same approach or pivot
            (Anti-oscillation in generator-handbook: same finding 3 rounds → MUST pivot)
            loop back to implement
    # No max R cap. Operator decides when to stop based on cost.
```

`MAIN deterministic merge` for `_evals/*-feedback.md`: blocking findings sorted by root-cause distance (matrix → criterion-fail → bug-list), ≤5 blocking + ≤5 hint, conflict detection between findings.

## 9. Vertical-slice three-layer enforcement

Per the user's earlier sign-off — three layers with non-overlapping coverage.

| Layer | Mechanism | What it catches |
|---|---|---|
| **Planner** (deterministic lint) | `spec_lint.py` L02 + L05 | feature naming has phase markers; sprint deliverables single-layer without explicit pure-* tag |
| **Generator** (prompt rule) | `generator-handbook` mandatory pre-implementation 3-question check | proposed contract verification is mock-only / single-layer |
| **Evaluator** (prompt rule + threshold) | `evaluator-handbook` contract-review + QA-time threshold | accepts contract draft missing user-observable verification; QA passes despite incomplete layer threading |

## 10. Anti-drift mechanisms

1. **spec.md immutable**: `block_pretool.py` rejects Write/Edit on `specs/_epic/spec.md` after `/init` completes. Only `/finalize` archive_batch can move it.
2. **contracts.jsonl append-only**: `block_pretool.py` rejects Edit (only Write that appends a line is OK). Implemented as a regex check on the new content vs old content.
3. **Helper-script-only mutation** for any new structured artefact: e.g., when ADRs are added during /loop, `feature_io.py`-style helper enforces shape.
4. **Transcript-as-evidence**: evaluator reading order is locked to spec → contract → transcript-slice → diff. Generator-authored narrative trace is removed from authoritative inputs.

## 11. No-escalate rationale (deliberate departure)

Anthropic v2 has no escalate mechanism. Per `Harness design for long-running application development`:
- Line 76: "if any [criterion] fell below it, the sprint failed and the generator got detailed feedback" — no max rounds, no escalate path
- Lines 162-170 (DAW table): 3 rounds converged naturally
- Line 50: generator strategic-decides "refine if trending well, pivot if not"

gan-harness adopts the same policy. The loop runs until evaluator approves. Operator stops externally (cost cap, ctrl-C). Removed from v1:
- `_escalations/` directory
- `status:deferred` / `status:escalated`
- `block-by-ancestor` propagation
- `/finalize` retro path
- max_rounds cap

`generator-handbook` carries the strategic-decision discipline as prompt-level guidance:
- "if score trending up: refine current approach"
- "if score stagnant or declining: pivot to a fundamentally different approach"
- "if same finding appears 3 rounds in a row: MUST pivot — no further refinement allowed on this approach"

## 12. /finalize (archive-only path)

```
1. preflight.py (now simpler):
     verify all sprints have phase:completed in contracts.jsonl
     no _escalations/ check (those are removed)

2. finalize_adr.py:
     proposed → accepted promotion
     retroactive supersedes backfill
     regen docs/adr/index.md

3. merge_domain_terms.py:
     extract new domain terms from spec.md
     append to CONTEXT.md (idempotent, lazy-creates)

4. regen_codemap.py:
     walk barrel docstrings → CODEMAP.md

5. archive_batch.sh:
     mv specs/_epic/ → specs/epics/<slug>/

6. summarize_batch.py:
     per-epic summary from contracts.jsonl + _evals/

7. single git commit
```

No retro path. /finalize either succeeds (all sprints completed) or refuses (some sprint isn't completed yet → "loop hasn't converged, run /loop more or stop the run").

## 13. ADR triggers

ADRs may be proposed at:
- `/init` by planner: when intent involves a hard-to-reverse architectural commitment
- `/loop` by generator (during contract negotiation or implementation): when a decision surfaces that meets the three-test gate (hard-to-reverse + surprising + real-trade-off)
- `/loop` by evaluator (during review): rare — when reviewing diff reveals an undocumented architectural decision

All proposed ADRs are promoted at `/finalize`. None during `/loop`. ADRs themselves are not the loop's deliverable — they're side-output of decisions that emerged.

## 14. Comparison: v1 vs v3.8

| | **v1 (current)** | **v3.8 (this design)** |
|---|---|---|
| Stages | 4 (`/prd` `/plan` `/execution-loop` `/finalize`) | 3 (`/init` `/loop` `/finalize`) |
| Agents | 4 (planner / fact-finder / generator / evaluator) | 3 + fact-finder optional |
| Spec format | `prd.md` (per-R sections) + `feature-list.json` (granular AC + must_not + eval_anchors) | `spec.md` only (high-level features as Markdown) |
| Per-sprint contract | none — AC pre-coded | yes — negotiated per-sprint, append to `contracts.jsonl` |
| Granularity of "done" | AC literal grep | criterion_mapping rolled up from verification_plan |
| Fail handling | `status:deferred` after 3 rounds → retro path | no max rounds; generator pivots; operator monitors externally |
| State tracking | `progress.tsv` + per-feature status field | `progress.tsv` + derived from `contracts.jsonl` |
| ADRs | `proposed` at `/plan`, accepted at `/finalize` | `proposed` at `/init` or `/loop`, accepted at `/finalize` |
| Vertical slice | `plan_lint.py L10a` (planner only) | three layers (planner lint + generator self-check + evaluator review/QA) |
| Evaluation criteria | implicit (AC pass/fail) | explicit 4 criteria from archetype template |
| Evidence for evaluator | spec + diff + generator's narrative trace | spec + contract + Claude Code transcript slice + diff |
| Anti-drift on spec | convention | block_pretool.py enforced immutability |

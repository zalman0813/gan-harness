Phase 1 — Spec 合規修補（堵漏洞）
最小改動、最高槓桿。刪除後門 + 加 lint 規則，不改流程架構。
A 關閉 Generator / Evaluator 的 3 個 Spec 修改後門
P0 小 Phase 1
›
問題
Generator 有 3 條路可以繞過 spec.md 不可變原則，悄悄修改 spec 邊界：
(1) _pending/*-amendment-v*.yaml 帶 reason: spec gap exposed
(2) generator.md:198–249 允許 generator 自行起草 ADR
(3) evaluator standards_axis.findings[].source: missing_adr 觸發 generator 寫 ADR
這些路徑讓 generator 在 loop 中悄悄擴展實作範圍，脫離 spec.md 錨定。
解法
結構性刪除，不靠自律：
• 刪除 amendment YAML 的 spec gap exposed reason（generator 不得以此 reason 提案）
• 刪除 generator.md:198–249 ADR 自寫邏輯
• 從 evaluator 的 allowed sources 移除 missing_adr
ADR 只能由 planner（/init 時）或 operator 授權的人工 ADR 起草。
改動檔案
.claude/agents/generator.md:159 .claude/agents/generator.md:198-249 .claude/agents/evaluator.md
B VP Anchor 多層強制（4 層 enforcement）
P0 中 Phase 1
›
問題
Verification Plan（VP）的每條斷言可以引用不存在於 spec.md 的 design doc 內容。
例：S08-draft-v2.yaml 裡出現 H-H3、K-H2 等 CONFORMANCE.md 代碼，data-testid 合約，ETag bump，這些都沒有 spec.md user story 的錨定。
解法 — 4 層防禦
  • L1 lint（spec_lint.py） — 每條 VP 步驟必須有 anchor: 欄位，缺席 → lint 失敗
  • L2 evaluator REVIEW_CONTRACT — 驗證 anchor: 的文字是否真的出現在 spec.md
  • L3 forbidden-token list — VP 不得出現 design doc 特定 pattern（如 CONFORMANCE 代碼格式 X-Y#）
  • L4 evaluator VERIFY — 執行時比對 anchor 覆蓋率，低於門檻 → FAIL

D ## Cross-cutting constraints H3 白名單 + spec_lint L09
P0 小 Phase 1
›
問題
planner 在 spec.md 的 ## Cross-cutting constraints 底下自由插入 H3 小節（如 CONFORMANCE-K divergence、Session-history phasing），這些是 planner 自己決定的 carve-out，使用者從未核准過。
目前 spec_lint.py 沒有規則約束此區塊的內容。
解法
## Cross-cutting constraints 底下只允許以下 5 種 H3：
Non-goals / Performance budget / Design language / Compliance / Domain terms

任何其他 H3（包含 CONFORMANCE 相關、phasing 相關）→ lint L09 失敗 → spec-finalizer 必須移除或改寫。

E References 限制 + 外部路徑 lint L10
P1 小 Phase 1
›
問題
spec.md 可以在正文任何地方引用外部文件路徑（如 design/CONFORMANCE.md）。
這讓 generator 看見 spec.md 就「合理推論」設計文件的細節是隱性需求，導致 VP 超譯。
解法
L10 lint 規則：spec.md 正文中出現的任何外部文件路徑，必須也列在 ## References section。
## References 裡的 entry 是使用者明確核准的參考，不在此的路徑 = 不應出現在 spec 正文。
planner 不得自動把 intent dump 之外的文件加進 References。

.claude/skills/init-workflow/scripts/spec_lint.py (新增 L10) .claude/agents/planner.md

Phase 2 — Research Pipeline 優化（CRISPY 架構）
解決 planner 同時持有「目標」和「問題空間」導致研究結果帶偏見的根本問題。
R1 Planner 拆分成 3 個 Subagent
核心 大 Phase 2
›
問題
現有 planner.md 有 85+ 條規則（超過 Dexter 的 150–200 token 指令預算），
且 planner 在生成問題時同時持有自己的 spec 草稿 → 問題帶有解法偏見（Gap A + Gap C）。
結果：research finding 確認的是 planner 的假設，而非真實未知數。
解法
拆成三個各 ~40 條指令的 subagent：
  • question-author — 輸入：intent dump only（無草稿 spec）。輸出：_questions.json。無解法偏見。
  • design-author — 輸入：intent + _research/*.md。輸出：_design.md（200 行）。
  • spec-finalizer — 輸入：使用者核准的 design + structure outline。輸出：spec.md。強制 lint。

R2 question_lint.py — 問題品質確定性 Gate
P0 小 Phase 2
›
問題
目前 _questions.json 由 planner 自由生成，沒有格式或品質 gate。
帶有目標語言（we want / should we / is it correct to）的問題 → 讓 fact-finder 回答意見而非事實。
解法 — 4 條 lint 規則
  • Q01 no-goal-language：拒絕 we want/we need/we plan/should we/is it correct to
  • Q02 no-design-asking：拒絕 recommend/suggest/propose/design/should…use
  • Q03 fact-form-required：必須以 What / Which / How many / Where / Does / Is 開頭
  • Q04 no-solution-leak：不得出現從 intent dump 提取的使用者功能關鍵字
MAIN session 在 lint 違規時拒絕 fact-finder dispatch → question-author 必須重寫。純 control-flow，無 prompt 信任。

Phase 3 — Anti-Scheming / Loop 行為強化
解決 generator 被觀察時乖、不被觀察時走捷徑、retry 重複同樣錯誤的問題。
S1 Trace-grounded Retry — 把 trace 片段注入 retry 上下文
P0 中 Phase 3
›
問題（Context Asymmetry）
Generator retry 失敗的根本原因：
Retry 的上下文 = {contract} + {spec.md 片段} + {evaluator finding 文字描述}
缺少：實際 trace（哪一行做了什麼）、error snippet、為什麼這樣設計的背景。
所以 retry 等同於用同樣輸入做同樣事 → 同樣錯誤。
Main session 能快速 debug，是因為它可以讀完整 trace。Generator 拿不到。
解法
Evaluator finding 加入 evidence_trace 欄位：
{
  "finding_id": "VP-03-missing-auth-check",
  "description": "...",
  "evidence_trace": {
    "file": "_traces/S08-gen-trace-R2.md",
    "step_range": "42-55",
    "snippet": "Edit src/auth.ts ... Error: 401 not raised"
  }
}
Generator retry 時，harness-loop 必須先注入 evidence_trace 內容，generator 讀完再動手。
這讓 retry 擁有和 main session 一樣的 trace 視角。

.claude/agents/evaluator.md .claude/schemas/eval.schema.json .claude/skills/harness-loop/SKILL.md
S2 行為一致性比對（宣告 vs 實際）
P2 中 Phase 3
›
問題（Fabricated Reasoning）
Generator 在 NEGOTIATE 階段宣告 done_looks_like[]，
在 IMPLEMENT 階段實際做了不同的事（走捷徑通過 gate），
但 evaluator 只看最終 diff，不比對宣告和實際的差異。
解法
Evaluator VERIFY 加入額外步驟（結構性比對，不依賴語意理解）：
  • 讀 contract.done_looks_like[]（NEGOTIATE 的宣告）
  • 讀 _traces/ 裡的實際 files_written + commands_run
  • 找：宣告了但沒做 / 做了但沒宣告 → 各自列為 finding

.claude/agents/evaluator.md .claude/skills/evaluator-handbook/SKILL.md
S3 Escalation Gate — 同 finding 連續失敗 → HALT + 通知
P0 中 Phase 3
›
問題
目前 harness-loop 沒有 escalation 機制（SKILL.md 第 17 行明確說「There is no escalate」）。
同一個 finding 在 evaluator 連續回傳 N 輪，loop 仍舊繼續送 generator retry，形成浪費。
Main session 有能力快速 debug 卻完全沒介入機會。
解法
Loop 終止行為：harness-loop SKILL 偵測到同一 finding_id 出現 ≥ N 輪 → 寫 _pending/S{NN}-escalation.md → SKILL return（loop 終止）→ main session 立刻回到互動模式，你可以直接打字 debug。

Escalation file 包含：sprint 號、finding 摘要、最近 trace 路徑、失敗輪數。

S4 Retry 約束收縮（Anti-shortcut Ratchet）
P1 小 Phase 3
›
問題（In-context Scheming）
研究顯示（arxiv 2603.01608）：鼓勵 agent goal-directedness 可讓 scheming 從 3% 跳到 59%。
Generator 在自主 loop 模式下，知道沒有人實時監看 → 優化「通過 gate」而非「做對」。
Retry 的上下文和第一次幾乎相同 → 同樣的捷徑思維。
解法 — 模擬「被觀察」的效果
正常輪（Round 1）：generator 有完整自由度。
Retry 輪（Round ≥ 2）：harness-loop 自動在 system prompt 注入額外約束：
# Retry constraints (round {N})
- You MUST quote the exact spec.md sentence that authorises each change
  before making that change.
- You MUST read the evidence_trace before touching any file in the finding.
- You may NOT create new files not listed in done_looks_like[].
這壓縮了 generator 在 retry 時的「捷徑搜索空間」。
改動檔案
.claude/skills/harness-loop/SKILL.md .claude/agents/generator.md
